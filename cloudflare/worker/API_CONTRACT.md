# K Media Telugu Worker API — implementation contract

This is an implementation contract for the staging-only Worker source. The current source implements health plus three public read routes, but is not deployed or connected to a D1 database.

## Public routes (after D1 parity is verified)

- `GET /api/categories` — list categories.
- `GET /api/articles?limit=&before=` — published articles only; bounded pagination using `published_at` as the cursor.
- `GET /api/articles/:slug` — one published article by slug.
- `POST /api/articles/:id/view` — idempotent view/session accounting for published articles only. Requires opaque `sessionId` and `visitorId` values (16–80 URL-safe characters) in JSON body; repeated session IDs do not increment views twice.

Public handlers must never return drafts, pending articles, rejected articles, admin records, private source configuration, or raw database errors.

## Admin routes (must remain disabled until authentication exists)

- `POST /api/admin/auth/*` — only after a supported identity provider and verified session strategy are selected.
- `POST /api/admin/articles`
- `PATCH /api/admin/articles/:id`
- `DELETE /api/admin/articles/:id`
- `POST /api/admin/categories`
- `PATCH /api/admin/categories/:id`
- `POST /api/admin/images` — R2 upload using server-side binding only.
- `GET /api/admin/analytics`

Every admin request must verify a signed, expiring session on the Worker. Authorization must come from a server-verified identity allowlist/role mapping. Never trust `is_admin`, an email, user ID, or role supplied only in request JSON or browser storage.

## Data and security rules

- Use prepared D1 statements and validate every path, query, and body field.
- Enforce `status = 'published'` in public article queries at SQL level.
- Apply request-size limits, image MIME/type/size checks, and rate limits.
- Set safe CORS origins to the production site only after cutover planning.
- Keep secrets in Worker Secrets; never commit credentials or Supabase service-role keys.
- Keep R2 private by default; serve objects through a controlled Worker or explicitly designed public custom domain.
- Return generic client errors; log operational details server-side without personal data.
- Implement view tracking with idempotency/rate-limiting to avoid accidental inflation.

## Dependencies before implementation

1. Verified D1 schema and imported data.
2. Chosen authentication provider and admin allowlist.
3. R2 bucket and object URL strategy.
4. Tested CORS, abuse limits, backups, and rollback.
5. Staging tests for current `admin.html`, `article.html`, homepage, and generated static article pages.

Until those dependencies are satisfied, the Worker must stay health-only.

## Existing website integration inventory (source inspected 13 Nov 2026)

The current `main` branch was inspected without changing production files:

- `admin.html` loads Supabase JS directly in the browser and uses OTP email sign-in.
- Admin authorization checks `admin_users` by the authenticated Supabase user UUID.
- Admin reads `categories` and `news_articles`; it inserts, updates, and deletes `news_articles`.
- Admin calls `get_article_unique_counts()` for unique-reader analytics.
- Article view counts are read from `news_articles.view_count`; the article page calls `increment_article_view(p_article_id)`.
- Images are uploaded to the Supabase Storage bucket `news-images`.
- Top Story state is currently stored as objects under `top-story/current`, `top-story/mode.txt`, and `top-story/custom-video.txt` in that bucket. The image upload path for article images is generated by the admin code and must be preserved during an object inventory.
- `article.html` reads only rows where `status = 'published'` and adds SEO/social metadata in the browser.

### Consequences for the Cloudflare replacement

1. A D1 `admin_users` table alone cannot replace Supabase OTP authentication. The existing login must remain on Supabase until a new identity/session flow is implemented and tested.
2. R2 migration must include all objects in `news-images`, including the three Top Story keys above, and preserve public URLs or provide a compatible URL mapping.
3. Worker API work must replace both RPC behaviors: `increment_article_view` and `get_article_unique_counts`.
4. The current frontend cannot be switched to D1 by changing only a database URL. All browser-side Supabase reads/writes, storage uploads, auth checks, and RPC calls need a coordinated API migration.
5. No Worker admin route should be enabled until signed sessions and server-side admin authorization are working.

No live website files, Supabase settings, D1 rows, or R2 buckets were changed by this inspection.

## Phase 2 implementation status (13 Nov 2026)

The Worker source now contains three public read routes, in addition to health:

- `GET /api/categories`
- `GET /api/articles?limit=20&before=<published_at>` (limit clamped to 1–50)
- `GET /api/articles/:slug`

All article queries enforce `status = 'published'` in SQL. Queries use prepared D1 statements. The Worker returns generic errors rather than exposing SQL details. No write, view-counter, admin, authentication, or image-upload routes have been added.

The routes require a D1 binding named `DB`. Until that binding is configured, data routes return HTTP 503. Health reports whether the binding exists. The example Wrangler configuration still has its D1 binding commented out.

## View tracking implementation status

The Worker now implements `POST /api/articles/:id/view`:

- Confirms the target article is currently published before recording anything.
- Uses the `article_view_sessions` composite key to make repeated requests from the same tab/session idempotent.
- Increments `news_articles.view_count` only when a new session row is inserted.
- Upserts an opaque visitor identifier into `article_unique_visitors`.
- Rejects malformed JSON, oversized request bodies, and invalid identifiers.
- Does not collect IP addresses, email addresses, or user-agent strings.

This endpoint is not a full abuse-prevention system. Before production use, add edge rate limiting/abuse controls and validate identifier generation/retention in the frontend. Client-provided identifiers can be reset or fabricated; analytics should not be treated as audited unique-person counts.

### Request example

```http
POST /api/articles/article-123/view
Content-Type: application/json

{"sessionId":"session_identifier_123","visitorId":"visitor_identifier_123"}
```

A response includes `recorded` (whether this request created a new session view) and the current `view_count`. It only counts published articles.
